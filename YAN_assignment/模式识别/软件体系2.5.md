## 📋 **架构风格选型速查表（按问题场景）**

### **场景一：你要处理“数据流”或“流水线作业”**
**典型需求**：数据从一个环节流到下一个环节，依次处理。
- **例子**：编译器、图像处理管道、ETL数据清洗、音视频转码。
- **首选风格**：**管道-过滤器风格**
- **为什么**：天然匹配“数据流动，依次处理”的模式。

### **场景二：你要做一个“用户交互型”的Web网站或管理后台**
**典型需求**：用户通过浏览器操作数据，有表单、列表、按钮。
- **例子**：电商后台、博客系统、企业ERP、学校选课系统。
- **首选风格**：**三层架构 + MVC**
  - 整体用**三层**（浏览器-Web服务器-数据库）。
  - 在Web服务器内部用**MVC**组织代码。
- **为什么**：这是Web应用的标准配方，分离清晰，易于理解。
- **备选**：直接使用**浏览器/服务器风格**（B/S）。

### **场景三：你要整合公司里“多个老系统”，让它们能互相调用**
**典型需求**：公司有财务系统（Java）、人事系统（.NET）、库存系统（Python），需要打通。
- **例子**：企业应用集成、政府系统对接、银行核心系统互联。
- **首选风格**：**面向服务架构（SOA）**
- **为什么**：SOA就是为**集成异构系统**而生的，强调标准协议和松散耦合。
- **注意**：如果系统都是新建的，优先考虑微服务。

### **场景四：你要做一个“高并发、需要快速迭代”的互联网产品**
**典型需求**：用户量可能暴涨，功能需要快速上线和更新。
- **例子**：电商平台、社交App、外卖系统、在线视频。
- **首选风格**：**微服务架构**
- **为什么**：
  1. 独立部署 → 快速上线。
  2. 独立伸缩 → 应对流量高峰。
  3. 技术异构 → 用合适的技术做合适的事。
- **前提**：团队有一定规模，有DevOps能力。

### **场景五：你要做一个“实时响应事件”的系统**
**典型需求**：某个动作触发后，需要立刻通知多方，或者需要松耦合的组件协作。
- **例子**：GUI桌面应用、游戏引擎、实时消息推送、股票行情系统。
- **首选风格**：**事件驱动风格**
- **为什么**：组件通过事件解耦，发布者不需要知道谁处理。
- **典型模式**：发布-订阅模型。

### **场景六：你要做一个“规则经常变”的业务系统**
**典型需求**：业务规则需要由非程序员（业务人员）频繁调整。
- **例子**：保险理赔计算、金融风控规则、促销引擎、专家诊断系统。
- **首选风格**：**基于规则的系统风格**
- **为什么**：规则（IF-THEN）可以从代码中分离，动态加载和修改。
- **核心组件**：规则引擎。

### **场景七：你要做一个“可扩展的桌面软件”**
**典型需求**：软件核心功能固定，但希望支持插件扩展。
- **例子**：IDE（如VSCode、Eclipse）、图像处理软件（如Photoshop）、音视频编辑器。
- **首选风格**：**平台/插件风格**
- **为什么**：核心平台稳定，功能通过插件无限扩展。
- **关键**：定义好平台和插件之间的接口。

### **场景八：你要做一个“资源不对等”的分布式系统**
**典型需求**：有中心节点存储核心数据/逻辑，多个客户端访问。
- **例子**：文件共享系统、早期网络游戏、数据库管理系统。
- **首选风格**：**客户机/服务器风格**
- **变体选择**：
  - 简单内部系统 → **两层C/S**
  - 需要更好扩展和维护 → **三层C/S**
  - 客户端希望免安装 → **B/S**
- **注意**：现在新系统一般直接用B/S或微服务。

### **场景九：你要做一个“层次清晰、每层职责明确”的系统**
**典型需求**：系统有明确的层次划分，下层为上层服务。
- **例子**：网络协议栈（TCP/IP）、操作系统内核、一些框架。
- **首选风格**：**层次化风格**
- **为什么**：强制分离关注点，易于理解和替换某一层。
- **缺点**：性能可能受影响（跨层调用）。

### **场景十：你要在代码层面解决“到处都要加的公共逻辑”**
**典型需求**：每个方法都要加日志、权限检查、性能监控，代码重复严重。
- **例子**：任何需要统一日志、安全、事务的中大型系统。
- **解决方案**：**面向方面编程（AOP）**
- **注意**：AOP通常**不单独作为整个系统的架构风格**，而是**辅助手段**，用在面向对象或分层架构中。

## 🎯 **高频场景考题与答案模板**

### **考题1：“设计一个电商系统（如淘宝），你会采用什么架构风格？”**
**答**：
1.  **整体上采用微服务架构**。因为电商系统业务复杂（用户、商品、订单、支付、库存等），且需要应对高并发和快速迭代。
2.  **在具体的服务内部**，采用三层架构或MVC来组织代码，保持结构清晰。
3.  **对于秒杀等高并发场景**，结合事件驱动和消息队列来削峰填谷。
4.  **对于促销规则等易变逻辑**，可以考虑采用基于规则的系统作为子模块。

### **考题2：“设计一个编译器，应采用什么架构风格？”**
**答**：应采用**管道-过滤器风格**。因为编译过程是典型的流水线：源代码 → 词法分析 → 语法分析 → 语义分析 → 中间代码生成 → 优化 → 目标代码生成。每个阶段处理上一阶段的输出，非常适合管道过滤器模型。

### **考题3：“公司有几个老旧系统需要整合，应选用什么架构？”**
**答**：应采用**面向服务架构（SOA）**。通过将各系统的核心功能封装为标准的服务（如Web Services），并使用企业服务总线进行集成，可以在不改动原有系统的情况下实现互联互通，解决信息孤岛问题。

### **考题4：“设计一个像Photoshop这样的软件，什么架构合适？”**
**答**：应采用**平台/插件风格**。将核心的图像处理引擎作为稳定的平台，将各种滤镜、工具、文件格式支持等功能作为插件来实现。这样既能保证核心稳定，又能支持功能的无限扩展和第三方开发。

## 🧠 **选型决策树（快速判断）**

面对场景问题时，按顺序问自己：

1.  **是数据处理流水线吗？** → 是 → **管道-过滤器**
2.  **需要集成多个现有异构系统吗？** → 是 → **SOA**
3.  **是大型互联网应用，需要快速迭代和高并发吗？** → 是 → **微服务**
4.  **是常规的Web管理后台或网站吗？** → 是 → **三层架构/MVC**
5.  **是桌面软件且需要插件生态吗？** → 是 → **平台/插件**
6.  **业务规则是否频繁变化且由业务人员定义？** → 是 → **基于规则的系统**
7.  **组件需要松散耦合、实时事件响应吗？** → 是 → **事件驱动**
8.  **系统有明显的层次依赖关系吗？** → 是 → **层次化**
9.  **以上都不是** → 考虑经典的**客户机/服务器**或**面向对象**。
