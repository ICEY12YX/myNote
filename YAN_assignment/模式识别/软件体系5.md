# 解决可用性
## 🏥 总比喻：把系统想象成**一家外卖餐厅**

- **用户下单** = 顾客点外卖
- **服务器处理** = 厨房做菜
- **系统故障** = 各种意外情况
- **目标**：保证餐厅**永远能接单、出餐**，不能关店

## 第一层面：冗余——**“多准备几个厨师和厨房”**

### 🎯 核心思想：

**关键岗位和资源都要有备份，一个坏了立刻换另一个。**

### 🍳 餐厅例子：

1. **主厨病了** → 副厨立刻顶上（**主备模式**）
2. **客流量大** → 3个厨师一起炒菜（**集群模式**）
3. **煤气灶坏了** → 马上换电磁炉（**设备冗余**）
4. **本店坐满了** → 引导顾客去分店（**多机房**）

### 📋 PPT中的解决方法（具体操作）：

1. **服务冗余**：
    - **做法**：同一个服务部署在多台服务器上
    - **比如**：用户登录服务，在5台机器上都部署一份
    - **效果**：哪怕2台机器坏了，还有3台能工作
2. **数据冗余**：
    - **做法**：同一份数据存多个地方
    - **比如**：顾客订单数据，同时在**北京机房**和**上海机房**各存一份
    - **效果**：北京机房着火了，上海机房数据还在
3. **双机/集群配置**：
    - **主备**：一个干活，一个看着（备机），主机坏了备机接手
    - **主从**：主机处理重要任务（写数据），从机处理次要任务（读数据）
    - **多主**：多个机器都能处理所有任务，互为主备
4. **关键点**（PPT强调的）：
    - **数据复制**：主厨的菜谱要实时抄给副厨（数据同步）
    - **状态检测**：如何知道主厨“晕倒了”？（心跳检测：每5秒问“你还活着吗？”）
    - **自动切换**：副厨如何无缝接手？（VIP漂移：把“主厨”的工牌挂到副厨身上）

## 第二层面：自愈——**“厨房小事故能自己处理”**

### 🎯 核心思想：

**系统出小问题时，能自己恢复，不用老板跑来处理。**
### 🍳 餐厅例子：

1. **厨师盐放多了** → 自己加点水稀释一下（**自动修复**）
2. **外卖员送错地址** → 自己重新送一趟（**重试机制**）
3. **收银机卡纸** → 重启一下就好了（**进程重启**）
4. **订单小票丢了** → 根据系统记录重新打印（**数据恢复**）
### 📋 PPT中的解决方法：
1. **超时重试**：
    - **场景**：外卖员给顾客打电话，**响了30秒没人接**
    - **做法**：挂断，**等10秒再打一次**（重试）
    - **关键**：不能无限重试（最多3次），不能影响其他订单
2. **数据恢复**：
    - **场景**：突然停电，正在炒的菜怎么办？
    - **做法**：
        - **事前**：每炒一步都拍照记录（**日志记录**）
        - **事后**：来电后看最后一张照片，接着那步继续炒（**从断点恢复**）
    - **现实技术**：数据库的WAL日志、Redis的AOF
3. **自动切换与恢复**：
    - **场景**：A厨师累倒了
    - **做法**：
        - **监控系统**发现A厨师5分钟没动（健康检查失败）
        - **自动叫醒**B厨师顶上（重启服务或切换节点）
        - **把A厨师没做完的菜**交给B厨师（状态转移）
4. **幂等性保证**（重试时的关键）：
    - **问题**：重试打电话，会不会被扣两次电话费？
    - **要求**：无论打多少次，只扣一次钱
    - **实现**：每个电话有**唯一编号**，系统记录“这个编号已打过”

## 第三层面：限流——**“高峰期控制进店人数”**

### 🎯 核心思想：

**人太多时，让一部分人在外面排队，别把餐厅挤爆。**
### 🍳 餐厅例子：

1. **排队取号**：店里只能坐50人，第51人开始取号排队
2. **预约制**：包间需要提前预约，不接受直接上门
3. **分时段优惠**：下午2-5点打折，分流午餐高峰客人
4. **限制每人点单量**：每人最多点3个菜，防止大桌占用所有资源
### 📋 PPT中的解决方法：

1. **流量控制**（控制总人数）：
    - **做法**：在餐厅门口设计数器
    - **规则**：
        - 店内<50人：直接进
        - 店内50-70人：发号排队
        - 店内>70人：“客满，请稍后再来”
    - **技术对应**：API网关限流，每秒最多1000个请求
2. **资源隔离**（把客人分类）：
    - **做法**：餐厅分区域
        - **VIP区**（付了包厢费）：保证有座位，优先上菜
        - **普通区**：正常排队
        - **外卖区**：单独通道，不占用堂食资源
    - **技术对应**：线程池隔离、容器隔离、微服务独立部署
3. **限流后的处理**：
    - **直接拒绝**：“对不起，现在客满”（返回错误页面）
    - **排队等待**：“您前面还有15桌，预计等待30分钟”（请求进队列）
    - **降级返回**：“您点的龙虾卖完了，换成基围虾可以吗？”（返回简化结果）
4. **具体技术**（不用记，理解原理）：
    - **令牌桶**：餐厅每秒发10个“就餐牌”，拿到牌才能进
    - **漏桶**：不管多少人排队，餐厅每秒只能服务5个客人（恒定速率）
    - **滑动窗口**：看**最近1分钟**进了多少人，而不是看整小时

## 第四层面：降级——**“特殊时期，只做招牌菜”**

### 🎯 核心思想：

**部分功能出问题时，主动关闭不重要的功能，保证核心功能能用。**
### 🍳 餐厅例子：

1. **煤气管道检修**：
    - **正常**：100道菜都能做
    - **降级后**：只做**不用煤气的菜**（电饭煲煮饭、凉拌菜）
    - **关闭**：所有需要爆炒的菜
2. **一个厨师请假**：
    - **正常**：同时做10桌菜
    - **降级后**：只接5桌，拒绝其他预订
    - **保证**：已接的5桌能按时上好菜
3. **外卖平台宕机**：
    - **正常**：线上线下都接单
    - **降级后**：只做堂食，不接外卖
    - **恢复后**：重新开放外卖
### 📋 PPT中的解决方法：

1. **依赖降级**（某个帮手不行了）：
    - **场景**：平时做菜要问“食材供应商”哪些菜新鲜
    - **供应商系统挂了**怎么办？
    - **降级方案**：
        - **备用数据**：用昨天的库存清单（本地缓存）
        - **简化流程**：不检查新鲜度了，有啥做啥
        - **固定菜单**：只做“永远有货”的5个招牌菜
2. **熔断降级**（彻底切断问题来源）：
    - **场景**：送餐合作方“美团骑手”系统全挂了
    - **现象**：连续10个订单都送不出去
    - **熔断触发**：
        - **关闭**：暂时不接所有外卖订单
        - **显示**：“外卖服务维护中，仅支持堂食”
    - **半开试探**：
        - 30分钟后，尝试接1单测试
        - 如果成功，慢慢恢复
        - 如果失败，继续关闭
3. **功能降级**（降低服务质量）：
    - **图片降级**：高清菜谱图 → 小图 → 文字描述
    - **推荐降级**：个性化推荐 → 热销榜 → 固定几个菜
    - **验证降级**：短信验证码 → 图形验证码 → 免验证
4. **手动/自动降级**：
    - **自动**：系统监控到错误率>10%，自动触发降级
    - **手动**：老板看情况不对，后台点一下“开启降级模式”

## 📝 一句话总结每个层面

- **冗余** = **“重要的东西都要有备份”**（多准备几套）
- **自愈** = **“小伤小病自己能好”**（不用总叫医生）
- **限流** = **“人太多时要排队”**（控制入口）
- **降级** = **“特殊时期只做最重要的事”**（保住核心）
## 💡 在软件系统中的真实对应

|餐厅比喻|软件系统|具体技术/方案|
|---|---|---|
|多备几个厨师|服务多实例|Docker容器、K8s副本集|
|菜谱多抄几份|数据多副本|MySQL主从、Redis集群|
|厨师累倒自动换人|服务健康检查|K8s的livenessProbe|
|电话没人接重打|调用重试机制|Spring Retry、重试队列|
|门口设排队栏杆|API限流|Nginx限流、Sentinel|
|分VIP区和普通区|资源隔离|线程池隔离、容器组|
|煤气坏了只做电炉菜|功能降级|配置中心动态降级|
|外卖全停只做堂食|熔断降级|Hystrix熔断器|

# 容灾
## 🏢 核心比喻：银行的总部与分支机构

- **生产系统** = 银行总部（正常运营的地方）
- **容灾系统** = 备用总部（以防万一的地方）
- **灾难** = 地震、火灾、停电、人为破坏等
- **目标**：总部出事了，备用总部能**立刻接手**，客户感觉不到中断

## 一、同城容灾（Local Disaster Recovery）

### 🏙️ 比喻：

**银行在同一城市的两个区各开一个总部**
- **总部**：西湖区总行（正常运营）
- **备用总部**：滨江区备用中心（随时准备接手）
- **距离**：10-50公里，开车1小时内可达

### 📌 关键特点：

1. **距离近**：同城，通常≤50公里
2. **延迟低**：两个机房用**专用光纤**直连，数据同步快（毫秒级）
3. **切换快**：故障时几分钟内就能切换
4. **成本较高**：需要租用同城另一个机房，拉专线

### 🛡️ 能防什么灾难？

- **单机房故障**（停电、空调坏、网络断）
- **小范围灾难**（楼层火灾、水管爆裂）
- **人为误操作**（某个机房配置错误）

### 🚫 防不了什么？

- **城市级灾难**（全城停电、大地震、洪水）
- **区域性网络瘫痪**

### 💻 技术实现（简单说）：

text

西湖区机房（主） ←--- 高速专线实时同步 ---→ 滨江区机房（备）
     ↓                                     ↓
   业务运行                           数据实时备份
     ↓                                     ↓
正常服务客户                         待命，数据随时可用

**切换过程**：

1. 西湖区机房断电了
2. 监控系统5秒内发现
3. 自动把“银行总行”的招牌挂到滨江区机房
4. 客户继续办理业务，几乎无感知

## 二、异地容灾（Remote/Geo-Disaster Recovery）

### 🌍 比喻：

**银行在两个不同的城市各开一个总部**

- **总部**：杭州总行
- **备用总部**：上海备用中心
- **距离**：200公里以上，完全不同的地理区域

### 📌 关键特点：

1. **距离远**：跨城市甚至跨省，≥100公里
2. **延迟较高**：数据同步有延迟（秒级）
3. **切换较慢**：需要手动或半自动切换（分钟到小时级）
4. **成本高**：需要完全独立的机房、网络、人员

### 🛡️ 能防什么灾难？

- **城市级灾难**（全城停电、大地震、洪水、战争）
- **区域性灾难**（全省网络瘫痪）
- **最彻底的防护**

### 💻 技术实现（简单说）：

text

杭州机房（主） ←--- 跨城专线/公网同步 ---→ 上海机房（备）
     ↓                                     ↓
   业务运行                           数据异步/准实时备份
     ↓                                     ↓
正常服务客户                         完整备份，可独立运行

**切换过程**：

1. 杭州发生大地震，机房全毁
2. 运维团队启动应急预案
3. 在上海机房**重建整套系统**（基于最新备份数据）
4. 通知所有客户：“请访问上海的新地址”
5. 业务恢复，可能有几分钟到几小时中断
